<objective>
Detect that the pilot has taken over a system MERLIN is commanding, and step back when it
happens.

Purpose: AUTH-05 and AUTH-06. Telemetry reports state, not provenance — "the pilot did it"
can only mean "nothing MERLIN sent accounts for it". D-12 accepts that and biases
deliberately toward sensitivity: a false positive costs one advisory window, a false
negative leaves MERLIN commanding an aircraft the pilot is already flying.

Three premises from CONTEXT had to be amended after research and are already settled:
`ProactiveMonitor` is never constructed, so the detector hosts on a direct
`TelemetryClient.subscribe` callback (D-11); `_extract_relevant_state` is an undo snapshot
covering 8 of 67 commands and cannot serve as the comparison basis, so a new watched-fields
table is written (RESEARCH B4); and 60 of 67 commands "verify" in roughly zero milliseconds,
so verification confirmation alone cannot open the watch (RESEARCH F2).

Output: verification checks for every observable command, a `has_verification_rule` helper,
`override_detector.py`, and its tests.
</objective>

    Then `class OverrideDetector` with the constructor and `on_telemetry_update` signature from
    this plan's `<interfaces>` block. Per-update algorithm:

      1. If `self._prev_state is None`, store the state and return. First frame only — the
         client initialises `_state` to a default `SimState()` with all zeros and False, so
         every field differs on the first real frame (F6).
      2. If `state.aircraft != prev.aircraft`, or `state.connected != prev.connected`, or
         `not state.connected`: store the state, set a settling deadline of
         `clock() + settle_s`, and return without detecting (F4).
      3. If a settling deadline is active and not yet passed, store and return.
      4. For each path in `WATCHED_FIELDS`, resolve on both `prev` and `state`. For floats,
         treat it as moved only when `abs(new - old) > WATCHED_FIELD_EPSILON[path]` (F3). For
         bools, moved when `new != old`.
      5. For each moved path, ask whether any recent dispatch accounts for it. Walk
         `sim_client.recent_dispatches()`; a dispatch `(command, t)` accounts for `path` when
         `path in COMMAND_WATCHED_FIELDS.get(command, ())` and
         `t <= now <= t + lead + grace_s`, where `lead` is `verify_timeout_s` if
         `has_verification_rule(command)` else `settle_s`. Two different leads is D-13 as
         amended: a command with a real rule may still be polling for up to the verifier
         timeout when its change lands, while a rule-less command "confirms" in roughly zero
         milliseconds and needs a fixed settle delay instead. Never treat a `verified=True`
         that no rule produced as evidence the aircraft moved.
      6. If at least one moved path is unattributed, that is an override. It is
         direction-agnostic by construction: any movement counts, because both directions mean
         the pilot is working that system (D-12). Call `authority.record_override()`; when it
         returns True, enqueue a `ProactiveEvent(type="authority", priority=1, message=...)`
         naming the system in pilot terms (gear, flaps, autopilot heading, COM1, and so on —
         map the dotted path to a human label with a small table) and log at WARNING.
         When it returns False the cooldown was merely extended; log at INFO and do not
         re-announce, so sustained pilot activity does not spam.
      7. Call `authority.take_restore_event()`; when it returns True, enqueue a
         `ProactiveEvent(type="authority", priority=0, message=...)` saying MERLIN has resumed
         its configured level, and log at INFO. This is the auto-restore half of D-14.
      8. Store `state` as `_prev_state`.
