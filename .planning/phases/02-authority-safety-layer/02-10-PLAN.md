<objective>
Put the authority state in front of the pilot.

Purpose: AUTH-08 is not satisfied by a JSON field. The phase goal says authority must be
"explicit, bounded, and never ambiguous", and four different situations produce the same
`advisory` level while calling for entirely different pilot responses: it was configured
that way, MERLIN detected the pilot taking over, MERLIN cannot reach the sim, or MERLIN's
own authority subsystem failed to start and it has restricted itself. An LED colour cannot
carry that distinction, so the indicator needs text.

Output: an authority indicator in the existing status LED group with a reason label, third
and fourth visual states for advisory and withheld command results, and a human verification
checkpoint — because whether this is legible in a cockpit-style display is not something a
test can assert.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server JSON → DOM | Status and message payloads are rendered into the page; unescaped interpolation of server-supplied strings is an injection surface |
| display → pilot | The last boundary in the phase. A correct authority state that the pilot misreads has the same operational effect as a wrong one |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-10-01 | Spoofing | Stale authority badge after the server becomes unreachable | mitigate | The `pollStatus` `catch` sets an explicit unknown state rather than leaving the previous value, verified in checkpoint step 7. Severity medium — a stale FULL badge tells the pilot MERLIN is armed when it may not be |
| T-02-10-02 | Spoofing | Advisory dry run visually indistinguishable from an executed command | mitigate | Distinct `cmd-advisory` class, non-success icon, and the `would_execute` value shown; verified in checkpoint step 4. Severity high — this is the pilot-facing half of RESEARCH B8 |
| T-02-10-03 | Tampering | Server-supplied strings injected into the DOM | mitigate | Render `message`, `safety_reason`, `would_execute`, `degraded_detail` and the reason label as text nodes or via `textContent`, never by string-concatenating into `innerHTML`. The strings originate in the orchestrator, but they embed aircraft names, command values and exception text that come from telemetry, from Claude and from arbitrary runtime failures. Severity medium |
| T-02-10-04 | Repudiation | An advisory drop and its restore passing unnoticed | mitigate | Level and reason changes between polls raise a toast through the existing helper, so AUTH-06's "informs the pilot" is satisfied in real time. Severity medium |
| T-02-10-05 | Elevation of Privilege | A display-layer control that changes the authority level | mitigate | This plan adds display only. No control is added, and `/api/status` remains `GET`. Authority changes only through configuration at startup, override detection and the watchdog. Severity high if violated |
| T-02-10-06 | Spoofing | A `degraded` authority state rendered as if it were a configured `advisory`, or conflated with the client-side unknown state | mitigate | `degraded` gets its own explicit branch and its own wording ("authority subsystem degraded" plus `degraded_detail`), the mapping has no default fallthrough, and the client-side unknown state is required to render differently. Severity medium — a pilot who reads "configured" when the truth is "MERLIN broke" will draw the wrong conclusion about whether the restriction is expected |
| T-02-10-07 | Information Disclosure | Rendering internal counters and exception text to the pilot | accept | `consecutive_timeouts`, `configured_level` and `degraded_detail` are shown only where they aid interpretation, on a localhost dev UI; the payload contains no credentials. Severity low |
| T-02-10-SC | Tampering | npm installs | accept | This plan installs no packages; the frontend has no build step or package manager. RESEARCH.md §Package Legitimacy Audit records zero new dependencies |
</threat_model>
